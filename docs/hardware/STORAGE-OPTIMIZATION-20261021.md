# 存储读取和传输前等待优化：固件 2.0.3

## 已实施

- 统一只读流 helper：为 FILE 本身配置独占的 16 KiB 内部 DMA stdio 缓冲。元数据扫描、BLE 文件读取和 HTTP 共用实现，不共享可变缓冲。内存不足时退到 8/4 KiB，再退到标准缓冲；完整性检查不变。未更改 SD 1-bit 接线、频率或 SDK 驱动。
- 保存已算出的音频 SHA：每条 136 字节、显式小端格式及 CRC 的可丢弃索引，绑定名称哈希、源头 44 字节哈希、大小/mtime 和解析后的音频范围。新录音完成时保存流式 SHA；旧文件首次扫描时补齐。索引损坏、缺失或不匹配会重算；写索引失败不把已保存录音报成失败。
- 改名/删除清除旧索引；接收端仍校验完整音频 SHA，不接受损坏音频。索引不是签名，也不承诺检测刻意保留头部、大小和 mtime 的中间内容修改；这种修改由最终全量 SHA 拒绝。
- 协议仍为 BLE 1.3，手机继续使用 1.2.27 / 235，无需为本轮改动重装 APK。最终固件 2.0.3 已构建、app-only 写入第二块板并验证，SHA-256：`44a891f1885a75b301c6ded7ef3fba58daeadb1ec5ce5e974344857eca7f8450`。

## 对照实验

测试同一块板、同一张卡和现有音频。第一组已返回 17 次结果；确认无缓冲方案明显退步后中止进一步扩大该组，不计中断中的请求通过。第二组完成 32 次。已返回结果的对应音频 SHA 均一致。临时测量命令只存在于隔离工程，不在最终固件中。

| 方向 | 6.78 MiB 音频 fread 累计 | 采用情况 |
|---|---:|---|
| 原路径 | 约 23.99 秒 | 对照，见前次分项计时报告 |
| 仅改变外层 fread 目标的内存/大小 | 小、中样本基本无改善 | 不采用 |
| 关闭 stdio 缓冲 | 0.24 MiB 就退步到约 6.38 秒 | 不采用 |
| FILE 使用 4 KiB 内部 DMA 缓冲 | 8.101 秒 | 内存不足时备选 |
| FILE 使用 8 KiB 内部 DMA 缓冲 | 5.503 秒 | 内存不足时备选 |
| FILE 使用 16 KiB 内部 DMA 缓冲 | **4.195 秒** | 默认采用 |
| FILE 使用 8 KiB PSRAM 缓冲 | 23.421 秒 | 不采用 |

单纯把外层目标改为 DMA 的收益主要在 SHA，不在真实 fread 路径。本次不把“PSRAM 可能退化为逐扇区读取”的静态推测当作已测得的唯一底层根因；确认有效的是给 FILE 配置内部批量缓冲。

## 正式候选验收

| 文件 MiB | 首次旧文件元数据往返（含补索引） | 重启后首个请求 |
|---:|---:|---:|
| 0.244 | 0.392 秒 | 0.256 秒 |
| 1.314 | 1.071 秒 | 0.263 秒 |
| 3.817 | 2.780 秒 | 0.255 秒 |
| 6.777 | **4.807 秒** | **0.210 秒** |

- 同连接内存缓存约 0.17–0.22 秒。旧文件的首次补索引仍需扫描，不声称首次导入所有历史文件都已经是 0.2 秒。新录音在保存时就生成索引。
- 新录音完成后未先查询元数据即重启，再查询约 0.304 秒、SHA 与完成事件一致；中文改名、完整/断点 BLE 读取并按 SHA 核对、自有测试录音删除通过。原有 29 个录音目录保持不变。
- 实际 Linux Wi-Fi DHCP、HEAD、7,106,604-byte GET 用时 **9.520 秒**（0.712 MiB/s）、完整 PCM SHA、范围/续传、错误 generation、凭据与路径越界拒绝、原网络恢复、热点关闭均通过。这是电脑端，不与先前 Android 的约 29 秒直接混算提升倍数。
- 真机第二轮实际接收 1,378,348-byte 文件：HTTP 响应 00:45:06.464，完整保存及 SHA 校验成功 00:45:09.663，相差 **3.199 秒**。系统连接确认在点击接收后 6.632 秒；该确认等待不包含在 3.199 秒内。首轮没有成功证据，不计通过。
- 热点切换断开无线调试；随后 USB logcat 读回的真实成功日志关闭了该项，不以自动化探针超时判断传输失败。后续调试连接仍有反复，不在本轮宣称已修好调试稳定性。
- 主机 ASan/UBSan：index roundtrip、逐字节损坏、所有截断长度、范围边界，以及既有 wire/range/WAV/source ring 不变量通过。固件编译的栈帧限制通过。
- 性能及真机测试候选 hash 为 `994e558ff9ce5f14ce7b3f523dfccbfc50d9ab067b654446c0cb22895db5b584`。交付检查发现 CMake SDK 应用描述版本仍为 2.0.2；仅同步该版本字段至 2.0.3 后重新构建、清除整个 factory 应用范围再写入和验证，形成上述最终 hash。最终镜像再次通过握手、目录不变和重启后 4 档元数据测试，6.78 MiB 为 0.171 秒。新增源码版本、SDK 描述及构建镜像一致性检查，避免未来再次漂移；读取/索引业务代码未在两镜像之间变更。

## 边界与交付

- 系统热点授权仍需用户确认，现有 Android 30 秒请求超时和板端 120 秒热点期限本轮未修改。文件读取提速不等于消除了这两个独立限制。
- 未进行真实物理断电、低电量、卡片拔插故障或全天长跑。坏索引的 CRC/截断拒绝由实际 codec 的主机测试验证，未故意破坏用户卡上索引。这里不宣称完整掉电原子性验收。
- 数值证据、最终 app 镜像和唯一一份测前应用分区回滚压缩件保存在 `output/hardware-storage-opt-20261021/`；不保留本轮完整 Flash/NVS 快照或临时测量工程。原有测试资料不清理、不移动。
- 未修改服务器、APK、UI、正式协议或其他服务；未提交/推送 Git。持久索引是正式功能，临时 benchmark 协议、探针和构建副本测后移除。

## 同日真机接收失败的定位与修复

- 这次失败与上述读取优化无关。Android 在 01:10:56 和 01:14:43 明确记录 `Request with wifi network specifier when wifi is off.Rejecting`；板端元数据及热点启动成功，约 0.2 秒后收到 App 关闭热点的命令，尚未传输音频。手机热点开启不等于 WLAN 客户端开关开启。
- 原生接收在申请板端热点前检查 WLAN，关闭时保持 BLE 就绪且不创建传输；接收层再检查一次，以覆盖中途关闭。页面仅给出“无线网络已关闭”和系统 WLAN 设置入口，不静默开启无线网络或自动重试。
- `Future.get()` 的连接回调错误解除 `ExecutionException` 包装；展示边界明确映射 WLAN 不可用结果，避免再次退化成通用桥接错误。系统取消后可再次接收，不遗留传输锁。
- 1.2.28 / 236 实测：关闭时提示及系统开关入口通过；开启后接收 2,077,740 字节，SHA 校验成功且页面显示“已接收”。该包的取消连接文案仍被通用映射吞掉，未以此包收尾。
- 最终 **1.2.29 / 237** 已覆盖安装到真机。重新验证：系统取消后正确显示“未能连接录音设备的传输网络。”，关闭提示后立即重试；接收 3,277,868 字节，01:31:16.314 返回 HTTP 200，01:31:47.224 完成保存和 SHA 校验，页面显示“已接收”，板端目录仍为 27 条。此为链路可用性验证，不作为速度提升证据。
- 最终 APK SHA-256：`5f6e20dd0f79b812cc3928d9c2d9f8f1ff3e39f513621a27d86f625d7caa362a`。硬件 JVM 58 项、消息/接收身份 Node 8 项、TypeScript、构建及既有 UI 门通过。

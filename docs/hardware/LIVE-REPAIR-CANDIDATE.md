## 为什么进入下一切片

当前安全行为是在首个 live sequence/offset 缺口处封住前缀，停止发送后续 PCM 给 ASR；结束后由 SD 完整补读并验证最终结果。这避免把错位数据或假静音当事实，但一个 Notify 缺口就可能让长会议后面的实时文字全部等到结束。5562 已出现源偏移 691200 的真实 GATT 缺口；同根 final 已恢复，不代表中途实时体验理想。这里改进的是实时连续性，不修改模型、声道、阈值或用户文案。

## 最小合同

- BLE 1.3 帧头保持不变。固件通过 `hello.capabilities.capture.live_range_repair` 明确声明能力；旧 App 忽略新能力，新 App 对未声明设备仍采用当前封口/最终补读。
- 新增控制操作 `capture.audio.read`，请求绑定 `session_id`、原 `stream_id`、偶数 `offset` 和 `length`。这是正在录制源的有界回读，不冒用已封存文件的 generation/SHA 合同。
- 单次最多 32768 bytes；只读同一活动 capture 已提交到 ring 的 PCM，保留范围以现有 256 KiB ring 为准。不从其他会话/任意文件读取，不分配整段会议缓存、不阻塞或暂停 SD 写入。
- 应答先提供独立 repair stream ID、绝对源偏移和精确长度，随后复用 Stored Audio `0x11`，范围内 sequence 从 1、最后一帧 FINAL。不得在 live stream 上重编号或将 repair 当新时间轴。
- 范围被覆盖、会话不匹配或资源忙时明确拒绝；不声称能无限回溯。只允许一个有限 repair 发送任务，断开/取消/停止需有明确释放路径。

## Android 所有权

- 同一 capture 的单个有界 assembler 管理连续 PCM 游标、后续暂存帧、待补范围和期限；它不是第二个录音 phase owner。
- 首缺口后暂存后续真实帧，同时异步请求缺失范围；字节、范围和源身份全部吻合才按原 offset 连续排出给现有本机镜像与实时 spool。绝不补零、压缩时间或抢先确认丢失字节。
- 有界缓存和独立期限失败后只封口一次，沿用当前最终全文件恢复和中文结果。旧 capture 的迟到回读/事件不得落进新 capture。
- 暂停不结束源；停止先终止/围栏旧 repair，再由现有完整来源校验完成，不引入双 writer 或第二条会议。
- 不改云端 realtime 协议；服务器仍只接收连续、原偏移正确的音频。服务身份、绑定、稳定事件和同根 final 逻辑不另起一套。

## 实施与证据顺序

1. 对 ring 快照边界和 mobile assembler 做纯函数测试：单包/连续多包缺失、重复、乱序、环绕、覆盖、取消、超时、暂停和跨 capture 围栏；所有成功路径逐字节等于原 PCM。
2. 在隔离虚拟外设中显式声明能力，注入单/多缺包；验证录制期间仍持续出现 durable 文字，且最终同根、全量 SHA。夹具不算实板证据。
3. 固件实现真实 ring 回读；主机 ASan/UBSan 和构建栈限制通过后，依既有 app-only 更新工具备份/写入。不得写 boot/table/NVS/eFuse/SD，保全当前 27 个用户文件。
4. Linux BLE 对实板在录制中请求各位置范围，逐字节对比最终 SD 源；同时录制不丢 I2S、控制操作不中断、资源可释放。
5. Android 候选仅对已声明能力设备启用；真机检查常规录制/暂停/保存/重连和完整接收。无法无损注入物理射频丢失时保留该验证边界，不冒称实板人为丢包测试通过。

如果测得控制补读影响 SD 或实时吞吐，应保留现有安全链路，不为达成测试数字而提高等待/缓冲到无界。

# 0033 全部接纳媒体导入与重叠转写编排

状态：已实施候选

## 真实证据

同一真机连续导入十条会议样本时，十条音轨均成功上传并创建转写任务，但旧实现暴露出两个容量域错误：

- 客户端把“同时准备两条”当成上传入口的接纳门限，第三条选择会被拒绝；
- 服务端只有一个离线转写编排协程，一条会议运行时其余任务全部排队，GPU 推理之间的 R2、解码和 VAD
  空隙无法被其他会议利用；排队任务在列表中还缺少“等待生成文字记录”。

## 决定

- 用户确认后的每条导入都必须先写 draft 和原生 ingest journal，并立即创建可见 meeting shell；上传入口不再
  因正在准备的数量而禁用。
- Android 仍按 meeting identity 加锁。React 只对昂贵的复制/音轨提取设置三个内部执行槽，超出的已接纳
  任务在持久 journal 上等待；进程终止后由同一 journal 恢复。
- `device_operations` 是转写任务恢复所有者，canonical transcript stage 是唯一界面投影。任务创建、排队、
  运行和失败都同步投影，列表与详情不得等首段文字出现后才显示状态。
- API 默认使用三个离线转写编排 lane，重叠 R2、ffmpeg 和 VAD 工作。8030 仍保留一个优先级推理协调器，
  实时会议优先，不通过复制模型增加显存。
- 三个数值是内部资源调度默认值，不是产品容量承诺；可通过服务端环境变量在 1–4 之间调整转写 lane，
  但客户端始终接纳可持久化的选择。

## 退出条件

- 连续选择十条时上传入口持续可用，十条均有稳定 meeting identity 和可恢复 journal。
- 排队、运行、完成、无人声和失败状态在列表与详情一致，状态单调推进。
- 多 lane 不产生重复 final、跨会议事件、游标倒退或 R2 cleanup 泄漏；实时 ASR 优先级不退化。
- 资源保护发生在内部调度层，任何内部满载都不得表现为“只能上传两条”。

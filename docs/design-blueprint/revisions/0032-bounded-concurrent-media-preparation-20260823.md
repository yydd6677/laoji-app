# 0032 有界并行媒体准备

日期：2026-08-23
状态：已被 0033 取代

## 问题

会议导入此前同时存在两层全局互斥：React Provider 的单一 `busy` 状态会在第一条录音准备期间
禁用上传入口，Android `MediaIngestor` 又使用一把进程级 I/O 锁串行所有会议的复制、视频抽音、
恢复和清理。结果是不同会议资产明明具有独立目录与 journal，仍不能并行，用户也无法继续选择下一条。

## 决定

- 本机同时活动的媒体准备任务上限固定为 2；第一条任务运行时上传入口保持可用，达到上限后才停止接纳。
- Android 将全局 I/O 锁替换为按规范化 meeting identity 分配的 keyed lock；不同会议可并行，
  同一会议的 stage/ingest/recover/acknowledge/discard/delete 继续互斥。
- 根目录创建和目录枚举保留极短的 root lock；文件复制、hash 和音轨提取不得持有 root lock。
- 每条任务继续先写持久 draft 和 ingest journal，再创建本机 meeting shell；并发不改变恢复、幂等、
  asset generation、WorkManager 或 R2 上传所有权。
- 应用启动时的 journal 恢复仍为短暂独占阶段，避免恢复结果与新选择竞争同一未完成来源。

## 用户结果

一条会议显示“正在准备录音”时，用户可以返回会议列表继续导入第二条。两条任务各自在自己的会议详情
显示状态。只有两条准备任务均未完成时上传入口才显示容量已满；任一任务进入后续阶段或失败释放槽位后，
入口立即恢复。

## 验证边界

- TypeScript 必须保留原子活动计数和上限 2，不得用单个布尔 `busy` 回退为全局互斥。
- Kotlin 合同必须保留按会议 identity 的 keyed lock，并禁止恢复 `mediaImportIoLock`。
- Release Kotlin 编译、Stage 2 Android 静态合同和双文件真机/专用模拟器回放通过后，才可称为运行验证。
- 两条同时准备不代表服务器 ASR 同时推理；准备、上传和转写仍是三个独立容量域。

# 蓝图修订 0001：现状基线与变革方向

## 证据边界

本修订只记录 2026-08-16 读取到的源码、文档和构建配置。它不宣称当前公网、真机或服务器已与源码一致。

已观察到：

- `app.config.js`、`package.json` 和 `android/app/build.gradle` 为 `1.1.10/118`。
- 当前工作树存在大量 modified、deleted 和 untracked 文件，不能直接作为可回溯发布基线。
- 会议整理 v3 已有事实协议、证据包、不可变版本、模板投影和持久任务实现，但长会议仍可能因证据预算 fail-closed。
- 客户端同时保留本地日程解析、服务端解析、多个会议 API/Provider 和旧兼容模式。
- 会议处理已经显式区分 capture、upload、transcript、summary、speaker 阶段，但展示和兼容代码仍横跨多个 store、mirror、provider 和 presentation 层。

## 设计判断

当前问题不是缺少更多局部门禁，而是“能力合同”和“实现链路”没有完全分离。若继续以当前目录、当前服务和当前模型为中心修补，会把历史兼容、旧状态和实验代码固化成未来架构。

## 目标候选 A：统一能力内核

建立一个设备范围的事件/任务内核：采集产生不可变媒体资产，阶段 worker 订阅资产事件，所有结果以版本和来源指纹提交；客户端只订阅投影。旧 HTTP、WSS 和数据库表先作为适配层，逐步退出业务逻辑。

优点：状态所有者清晰、可恢复、可取消、适合并行；缺点：迁移面大，需要重新定义客户端和服务端边界。

## 目标候选 B：本机记忆运行时

将日程、录音索引、笔记、转写草稿和任务状态统一放入本机事件日志；服务器只接收经过授权的处理请求和生成式结果，服务不可用时本机仍保持完整可读。跨设备能力不再作为架构前提。

优点：隐私和离线体验强、同步冲突显著减少；缺点：设备损坏恢复和云端任务续跑需要新的导出/恢复协议。

## 目标候选 C：证据图与可组合服务

把转写片段、人工笔记、附件和用户修正作为不可变证据节点；日程解析、整理、行动候选和问答都消费同一证据接口。图结构只用于路由和关系索引，最终显示必须回到原始片段。

优点：能统一引用、问答和整理，减少跨服务重复检索；缺点：索引更新、删除和资源占用需要严格设计，不能直接照搬大模型 GraphRAG。

## 下一次架构决策

先对 A/B/C 做能力覆盖、延迟、质量、资源、迁移和复杂度的同输入对比，不先决定使用哪一种模型或框架。若某候选不能减少概念和状态数量，即使局部指标改善，也不得作为目标架构。

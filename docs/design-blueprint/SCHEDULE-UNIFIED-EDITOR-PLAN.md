## 3. 用户旅程与页面合同

### 3.1 唯一编辑器

- 普通加号直接打开统一编辑器，不先询问手动还是语音，不自动开启麦克风。
- 日期格/明确时段上的创建动作，携带该日期/时段作为可见入口上下文。
- 手动字段、自然语言文字、手机语音、已完成转写的硬件日程都修改同一个draft。
- 既有日程从详情“编辑”进入同一个页面，绑定明确eventRef及重复日程编辑范围。
- 保存只有一次本机commit；不再进入只读确认页面或第二次保存确认。

### 3.2 页面构成

1. 固定顶栏：取消、保存；保持当前主题与安全区owner。
2. 可滚动主表单：标题、日期、时间为第一层；地点、提醒、重复紧凑排列；备注和低频选项按需展开。
3. 底部输入dock：常态仅显示清楚的麦克风和可切换的自然语言文字入口，不预留半屏空白，不加示范句、教学段落或AI解释。
4. 开始采集后，dock内显示真实录音反馈、结束/取消操作及本次识别文字；表单与顶栏仍在原页面。未保存的输入和字段不因为收起dock消失。
5. 键盘与录音区协调，不能同时堆叠；用正常resize/滚动保证焦点可见，不靠缩小字体或缩短触控区腾空间。
6. 初始空白编辑器不自动弹键盘；点标题再输入。解析返回不能抢焦点、重建EditText或滚回顶部。
7. 录音先本机起采，再异步连接已有日程WSS。保留早到音频，不把服务握手放在按键响应前。
8. 字段应用只局部更新；对真正变化的字段给短暂非布局强调。只保留一次“撤销”操作，不增加“已更新N项”等重复提示。

## 4. 时间精度与显示合同

### 4.1 新业务表示

```ts
type ScheduleTimePrecision = 'unspecified' | 'period' | 'exact';
type SchedulePeriod = 'early_morning' | 'morning' | 'noon'
  | 'afternoon' | 'evening' | 'night';

type ScheduleTimeValue =
  | { precision: 'unspecified'; period: null; startTime: null; endTime: null }
  | { precision: 'period'; period: SchedulePeriod; startTime: null; endTime: null }
  | { precision: 'exact'; period: null; startTime: string; endTime: string | null };
```

使用现有六个period值，显示凌晨、上午、中午、下午、傍晚、晚上；“早上/早晨”属于morning的表达别名，不为标签再建一套时段。若后续发现用户需要独立“早上”精度，再单独决策，不在本次任意扩枚举。

- 新draft允许日期为空，已保存CalEvent仍须合法startDate。时间值必须满足上述互斥协议。
- `CalEvent`新增同义的持久`timePrecision`、`timePeriod`字段；exact同时保留现有startTime/endTime以沿用索引及提醒。不得把时间只留在rawText或native snapshot。
- period不映射成固定小时或虚构起止区间，也不当成全天。
- unspecified显示“未设置”；不等于“待补充错误”，没有具体时间本身不阻止保存。
- 只有开始时分合法，不强制结束。结束时分存在时须有开始时分，跨午夜须有明确结束日期。
- “只有下午”不能生成一个假造的精确提前提醒。保留用户明确配置的提醒偏好，但执行具体提醒必须有可执行时间；清除时间时在同次状态变更中清理失效的提前提醒，不造成表面可保存、提交再报错。
- 精确09:23必须在进入/退出选择器、语音补改、保存、重开后保持09:23。分钟选择采用0–59，不在state初始化或显示时snap为5分钟。

### 4.2 全天处理

- 从新建和编辑产品UI删除全天开关、全天选项、取消全天后的第二套未设置状态。
- 不再用`没有startTime => isAllDay=true`作为业务推断。
- 新输入明确说“全天培训”时保留这段事项/原话及日期；本次精度为unspecified，不捏造00:00–24:00，也不声称提供忙闲阻塞语义。
- 历史`isAllDay`值不批量销毁。未修改时间的旧记录保存时保留原数据；用户明确改成period/exact时才清掉旧flag。新界面的无时分显示统一为“未设置”。
- native日视图“放在无钟点区域”的layout标志与业务全天不是一回事。可暂保留既有wire布局字段，但禁止由它反向重建业务timePrecision；读者必须用精度/period显示。不要为字段名一致重写整个日历渲染器。

### 4.3 全部消费者

主编辑、时间子页、月/日历、搜索、详情、重复展开/例外、待办采用为日程、硬件输入恢复、提醒validator和JSON序列化必须一致。无时分事件留在无钟点区域并显示真实时段，不偷偷放到19:00网格。历史“从rawText推时间”仅可在明确legacy适配边界使用，不能继续对新版本已编辑事件调用，否则旧原话会覆盖新时间。

## 5. 日期默认不是任意概率填空

初次解析按以下顺序决定日期：

1. 本次表达中的明确日期；
2. 用户明确在某一天/时间格发起创建的上下文；
3. 没有任何日期表达且没有延期语义时，使用本次输入参照时区的当天作为产品默认。

全局加号不能无声继承用户刚浏览的历史日。后续补改没有提日期就保持当前draft日期，不重新套“今天”。“改天/日期没定/下个月找时间”是明确未定，不是省略日期：保留日期待选，不能硬落到今天。

- 每次输入固定captureStartedAt/referenceDatetime/timezone；跨零点、重试、模型回复变慢不能改变该次输入的相对日期。
- hardware使用录制时刻和时区，而不是接收日期。原板端无可信时钟保护继续有效，不能用本方案的默认今天绕过它。
- 晚上、下午等只决定period；不根据当前时刻暗自把今天推到明天，也不以模型自报置信度决定保存。
- 推定值可直接出现在编辑字段，用户可立即修改；不加“AI判断概率xx%”或永久解释旁白。
- 缺少真正必填日期时直接在日期行选择，不切到独立补充问答，不阻断其他字段编辑。现有字段合法性校验继续保留，移除`needs_clarification`一个布尔值控制整页保存的方式。

## 6. 同一份草稿与生命周期

在现有日程域新增单一`ScheduleEditorDraft`（具体文件名可用当前owner整合，不建第二服务层）：

```ts
interface ScheduleEditorDraft {
  id: string;
  revision: number;
  mode: 'create' | 'edit';
  eventRef: EventRef | null;
  recurrenceScope: 'occurrence' | 'following' | 'series' | null;
  sourceInputJobId: string | null;
  sourceKind: 'manual' | 'phone_voice' | 'hardware_voice' | 'meeting_action';
  startDate: string | null;
  endDate: string | null;
  time: ScheduleTimeValue;
  title: string;
  location: string;
  notes: string;
  // recurrence/category/reminder沿用现有可用表示，不把复杂重复规则缩成once。
  fieldOrigins: Record<string, 'manual' | 'explicit' | 'context' | 'default' | 'legacy'>;
  inputSequence: number;
  latestInputText: string;
  phase: 'editing' | 'recording' | 'parsing' | 'saving' | 'saved';
}
```

`phase`是编辑会话的单一状态，不是新建全局任务总线。React与native投影同一revision；不得分别保存第二份可推进的phase。原生EditText的正常本地输入即刻反映到草稿，不能每个level回调重建表单。

结构化字段变更才增加draft revision；录音音量、phase、转写文字增量、焦点变化不使自己的请求失效。operation sequence单独递增。`mode=create|edit`是草稿与事件的关系，`inputMode=initial|patch|replace`是当前输入的用法，两者不得混用；replace既有事件的草稿仍绑定原eventRef，不变成新建。

### 6.1 持久恢复

独立日程库schema3增量升级到4，在现有初始化owner执行；不得改旧迁移文件或重建/清空数据库。

新增一张`schedule_editor_drafts`表，建议列：`id PRIMARY KEY, state, revision, draft_json, input_job_id UNIQUE NULL, event_ref_json NULL, pending_input_json NULL, last_undo_json NULL, save_request_id, saved_event_ref_json NULL, updated_at_ms`。字段状态由CHECK或TS严格验证；一个硬件job只能绑定一个draft。已有事件时间字段存event_json，不为本次精度引入另一事件表或跨库写入。

- draft变化使用有界短合并写入；应用patch、退后台/离开、开始保存是必须落盘边界。不要在主线程同步加密/序列化大量历史。
- 同一草稿至少保留本次输入文本、参照时间、revision及pending operation，重开可继续，不自动发送旧语音或重复保存。
- 进程重建后未完成的模型请求回到可重试状态，保留草稿和文字；不假装模型还在后台持续工作，不新造服务器持久日程副本。
- 正常返回不丢草稿；用户明确“放弃”才删该草稿。按现有退出保护整理成一个owner，不能一次返回弹两层确认。
- 新建新草稿与恢复旧草稿的选择只在确有未完成内容时出现，不做全局草稿管理新页面。

### 6.2 迁移前数据备份

本机安装的`expo-sqlite`实际提供`backupDatabaseAsync`。首次schema4升级前，复用日程写队列屏障，使用SQLite backup API创建app-private单次schema3快照，验证`integrity_check`、事件数量与原事件ID。不能只拷贝活跃WAL主文件，也不能因快照失败而清库重试。备份不发服务器、不含会议库/音频，留存路径记录在本机迁移元数据；同一升级不反复复制。真机无法提前导出私有库时如实标pending，由安全迁移过程完成，不能把源码归档当数据库备份。

schema升级失败须回滚本次事务，原schema仍可读。若成功升级后需要回退，旧315不能直接读取更高schema：必须先处理升级后新增/编辑数据，再决定恢复快照或用归档源码构建兼容版本；不得把旧APK、clear-data或强行降低user_version当无损回退。

## 7. 初次生成与语音补改

### 7.1 初次生成

复用现有采集/ASR、`parseText`及MentionGraph。简单高置信输入可本机处理；复杂初始输入继续唯一graph模型路径，不恢复旧服务器规则二次解析。把解析观察映射到统一draft后应用日期默认；原`needs_clarification`转换成字段级待选/错误，不继续支配页面流转。

模型声明了重复但缺少有效原文依据，或其重复无法进入当前合同，不得降级成一次性安排；本次观察无效时保留原草稿和输入。没有有效观察属于内容失败，不能假报为Provider不可用；真正的网络/模型运行异常仍按服务失败处理。这不改变语义门，不把拒绝坏观察计作原本安排已正确解析。

### 7.2 补改不能拼接历史原文重算

当前`/schedule/graph/clarify`将原文和“补充：...”拼起来解析，不能表达手动编辑后的真实草稿。本次新客户端不再调用它来补改。

在既有v2 graph路由族内增加`POST /api/device/v2/schedule/graph/edit`，仍使用当前设备鉴权、`LlmProvider`、资源优先级及当前本地/云端可交换合同；不新增进程、模型或Provider回退。与当前纯计算parse一致，不把完整草稿写成服务器日程。

请求协议（Pydantic与TS同步）：

```json
{
  "schema_version": 1,
  "client_request_id": "draft-edit:<draft-id>:<sequence>",
  "draft_id": "...",
  "base_revision": 7,
  "input_sequence": 3,
  "reference_datetime": "带时区的本次采集开始时刻",
  "timezone": "Asia/Shanghai",
  "mode": "patch",
  "utterance": "本次转写或自然语言文字",
  "draft": {"当前可编辑字段": "当前值，而非最早解析值"}
}
```

响应含`draft_id/base_revision/input_sequence`原样回显、`status=patch|no_change|unsupported|ambiguous`及至多16个changes。每个change包含允许的字段组、`set|clear`、类型化value及对应本次原文依据。字段组限title/date/time/location/notes/category/recurrence/reminder；不接受任意JSON路径、eventId、用户数据删除指令或UI代码。

- `set time`必须给出完整互斥时间值；`clear time`是unspecified。其他字段不出现就保持不变，不能把“没提到”当null清除。
- `clear location/reminder`仅在用户明确要求时发生；不能因模型返回空值把手动字段擦掉。
- “晚一小时”允许基于当前确切时间计算；原草稿只有“晚上”则不能编出时点，应保持可见待选。
- “周五下午”在已有有内容草稿中是对当前日期/时间的补改，不因缺动作词判成新建失败。
- 由模型判断用户本次修改的语义，不堆样本关键词否决；确定性代码只验证协议、日期时间合法性、字段依赖及revision。
- 若给来源offset，统一明确为UTF-16 code unit以匹配现有客户端slice；服务端不能把Python codepoint索引原样当UTF-16。引用仅来自本次utterance，不能伪造新日期的“逐字依据”。结构化当前draft作为计算上下文，不冒充用户本次原话。
- 每次正常远端补改一次模型生成；不增加逐字段模型调用、反思循环或模板二次生成。结构无效保留草稿和本次文字，允许明确重试，不自动无限修复。
- 输出只是一份patch建议；只有本机校验成功才应用。模型不负责提交日程、判断UI能否保存或选择另一个事件。
- 初期能力协商增加版本化edit/time合同；缺能力时保留本机编辑及文字，不静默回旧clarify，不切另一Provider。
- edit的`mode`只接受`patch`；重新输入不发送当前草稿到该接口，而是复用7.1的初次观察。移除尚未采用的server replace语义，避免省略字段既被解释为保留、又被解释为清空。
- 315是当前真实存量客户端，因此服务端旧clarify接口可保留必要兼容；新APK完全停用它。记录确切旧caller再退役，不保留新客户端备用分支，也不在发布新包前破坏用户仍安装的315。

## 8. 异步结果、手动编辑、撤销与重说

### 8.1 应用fence

一次录音或文字提交绑定`draft_id + base_revision + input_sequence + operation_id`。响应到达时要求当前仍为同一草稿、同一有效operation，且保存/放弃均未开始。

第一版采用明确的整份revision CAS，而不是让模型猜字段锁：请求期间手动改动使base_revision过期时，不应用旧patch、不自动重跑模型；保留本次文字，可直接重新应用到最新草稿，无需重录。UI不冻结表单，不展示版本号或“锁冲突”。本机同步字段修改不受网络等待影响。

原生输入还须防止桥接回写落后于当前键入：字段和文字dock的本机修改携带当前View实例的递增token，JS将实际处理过的最新token随快照确认；未确认最新本机修改的旧快照不得重写文字或草稿。确认后同样拒绝乱序旧回写，但允许同一当前确认下的撤销、模型结果和其他合法字段更新。此token仅是短期显示层确认，不持久化、不替代业务revision/CAS，也不靠失焦、输入延时或丢弃键入节流绕过。

录音/解析期间保存保持原位但不提交；用户可以结束并等待本次输入，或取消本次输入后立即保存已有草稿。不能把点击保存偷偷解释为丢弃正在说的内容，也不能提交旧内容后被晚到结果改写。已接受的本机commit不再接收该次输入的结果。

### 8.2 语义变更是原子的

先把全部patch应用到内存候选并校验，再一次性提交新draft revision；不能一半日期成功、一半时间失败。跨日变更、清除提醒和时间精度切换属于同次事务。无效提议不降级已有合法draft，也不把整页换成错误页。

### 8.3 撤销与重新输入

- 只保留最近一次语音patch的逆变更。撤销不删除用户之后手动修改过的字段；不满足可逆条件就保持当前内容，不从整份旧快照覆盖新输入。
- “重新输入”收在dock次要操作中，明确启动replace模式。录音取消/失败原draft不变，新结果形成后才原子替换。
- replace只解析本次表达，复用`parseText`与初次字段映射，一次解析形成完整内容提议；不调用graph/edit，不将旧地点、备注、类别、重复、提醒当作新输入的默认。省略日期按本次固定参照时区的当天处理，明确未定保留空；旧草稿的手改日期不是新输入的入口上下文。日期策略仍使用5节的同一owner，不另造日期猜测器。
- 本机要求replace覆盖全部可编辑内容字段，缺字段或不合法时不应用。草稿id、eventRef、事件revision、重复编辑范围、来源job和保存requestId保持；既有事件仍是编辑，不新建第二条。新内容清掉旧全天兼容flag，一次撤销可恢复原内容和来源，后续手改仍优先。替换不在开始录音时清空表单。
- replace不是普通麦克风的默认动作；不用每次询问用户“补充还是重说”。
- 麦克风补改当前单条，不能根据一句话偷偷新建第二个日程或操作另一条记录。多事件或全局查询/删除留在非目标范围。

## 9. 时间子页详细交互

1. 时间精度使用单一选择owner：未设置/时段/具体时间，不再有全天、具体时间、结束时间三个互相牵制的模式开关。
2. 未设置：无小时/分钟滚轮，不展示“结束未设置”占位；日期仍可通过主日期行编辑。
3. 时段：选择现有六个时段，清楚显示所选；没有时分轮和结束时间区。设置时段不强制用户补钟点。
4. 具体时间且未添加结束：只显示日期/小时/分钟三列滚轮及“添加结束时间”入口；开始/结束双摘要和分隔线全部GONE，不用透明/INVISIBLE留空。
5. 添加结束后才出现开始/结束切换，共用一组滚轮。关闭结束清除有效endTime；原结束日期若仅因结束时分存在而产生，则同次清理，真实用户设置的跨日日期范围不能误删。
6. 进入/取消不更改值；手动启用具体时间可给一个可见滚轮候选，但只有点完成才提交。不得把显示用10:00/11:00当已经接受的值写入draft。
7. 结束不晚于开始时指出相关字段，不自动给用户加一小时或暗推次日。用户明确说“到明天一点”应正确形成跨午夜范围。
8. 时间子页返回只丢弃本次子编辑，不丢主草稿；不返回旧语音页。

## 10. 保存、本机权威和硬件接纳

- `EventsStore`和独立日程repository仍是唯一事件写者，UI与模型服务不能直接写第二份事件表。
- 每个editor draft固定save_request_id；创建重试复用它。编辑绑定eventRef和基线revision，不因语音补改变成另一次addEvent。
- 编辑的原`eventRef`与基线revision是目标校验栅栏，保存后的`savedEventRef`是事务内实际结果地址：sourceEventId保持不变，改期或修改整组重复时occurrenceDate可改变；单次/后续例外仍按既有例外锚点解析。回执必须能在同一事务的事件行中解析并匹配草稿，不能继续保存已失效的旧地址。重放先读持久回执，不因旧地址不再存在而重复写事件。
- 编辑器保留本次进入时的不可变编辑基线；自己的事件投影发布、改期或提醒刷新不能将仍在保存的编辑器卸载。正常保存和已保存草稿恢复都使用回执地址回到唯一详情页，不叠加旧地址详情页；后续外部更改仍由revision冲突校验处理，不能靠冻结基线绕过。
- 同一保存请求不能携带两种payload。保存结果未明时先恢复该请求的本机回执；若已创建就绑定原eventRef处理后续编辑，不另起requestId制造第二条。保存phase禁止字段提交变更，非保存期仍正常编辑。
- 保存提交与draft完成回执要在日程写队列中协调。优先使事件写入、draft saved及source input job完成处于同一SQLite事务/可重放use case；如现有EventsStore整表persist限制原子性，先把该提交收敛到同一个已有repository事务入口，不能让UI直接SQL绕过它。
- 宕机窗口最少保证：已提交事件可按clientRequestId找回，重开只补完成回执，不创建第二条。投影刷新和提醒重算不能反过来否定已经成功的本机commit，沿用315修复原则。
- 硬件ScheduleInputProvider仍接纳/转写原source；ready job交给统一editor，`input_job_id`唯一防重复打开/保存。取消编辑不删除源录音；只有本机事件提交及接纳回执成立后才按现有合同acknowledge，不能恢复旧“手动加入会议”流程。
- 待办采用为日程继续保持原clientRequestId、followup关联和完成联动，不增加单独确认页。
- 待办来源身份与待补齐关联保存在同一草稿JSON，随事件提交的saved回执一起落盘；关联写入会议库失败不撤销日程、不把已保存表单困住，也不提示用户重复保存。现有日程生命周期owner在启动、前台和提交后重放关联，使用有界退避；只补关联、不重写日程。会议/待办已删除或已关联另一条时停止，不覆盖现有关系；日程已删除时不得复活。关联完成使用自己的attempt fence，不改变已发出的编辑提交回执版本。
- 不修改录音板固件、BLE协议或长按/双击手势，本次只替换手机的日程编辑承接。

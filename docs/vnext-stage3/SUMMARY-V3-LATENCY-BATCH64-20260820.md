# Stage 3 Facts V3 长会延迟与 embedding 批处理证据

## 结论

本轮只把长会证据包的 embedding 默认批次从 16 提高到现有上限 64，并增加不含正文的 provider
遥测。Facts V3 提示词、r9 事实协议、模型、输入预算、MMR、校验和本地投影均未改变。同一 Android
长会结果的规范化文档 SHA-256 完全相同，任务总时长从约 99--101 秒降到 66.46 秒。

状态仍为 `isolated candidate evidence; not adopted`。没有修改生产 `18020/8030`、GPU1、PCB、
Smart Meeting、真机或公网流量。

## 基线分解

专用 `emulator-5562` 使用 1,357 个稳定转写片段的
`vNext 验收夹具·股权会议（SRT参考）`，经隔离 API `18023` 运行。批次 16 的两次相同来源回放：

- 进程恢复回放：任务总时长约 `98.97s`，attempt 约 `96.32s`。
- 遥测基线回放：任务总时长约 `101.02s`，attempt 约 `96.71s`。
- 第二次回放的单次模型调用为 `68.53s`：prompt `8,669` tokens / `2.09s`，生成
  `4,096` tokens / `35.15s`，load/context `19.83s`，排队约 `0.23ms`。
- 模型以 `done_reason=length` 结束，输出 16,266 bytes。确定性截断修复保留 9 条可验证事实，关系和
  行动候选均为 0；未触发第二次模型修复调用。

这证明主要耗时不在 prompt 编码，而在证据 embedding 的多次调用、Ollama 上下文准备和完整 4,096
token 解码。

## 被拒绝的输出限额实验

曾隔离试验把单次生成压为 8 facts / 8 relations / 4 actions，并增加字段长度约束；生产提示词和候选
服务均未采用。既有 9 组真实字幕 holdout 仅 `8/9`，`equity` 在允许的一次修复后仍为
`SUMMARY_V3_FORMAT_INVALID`。完整负向报告为 `facts-v3-r10-holdout-20260820.json`。相关源码已用补丁
恢复为 r9，防止为了速度牺牲结构可靠性。

## 仍未通过的门

- 当前长会仍顶满 4,096 输出 token，关系和行动候选可能在数组顺序末尾被截去；这既是质量问题，
  也是剩余约 31 秒解码成本，不能因任务低于 90 秒就忽略。
- 66.46 秒只是单次真实回放，不是 p50/p95 分布；Stage 3 延迟门仍未关闭。
- 独立人工事实支持率、行动有效性和 Q2 引用相关性仍未达到可证明的 95%。
- capability barrier、旧流量排空、全量迁移及 Stage 2 ASR 性能阻断均未关闭。

## 隐私与回滚

新增遥测只保存 provider、operation、调用数、token 数、纳秒时长、结束原因和输出字节数；不保存或
返回 prompt、会议正文、模型正文、标题、人物、引用、附件名或坐标。批次仍可通过
`SUMMARY_V3_EMBED_BATCH_SIZE` 回退，范围限定为 4--64；回退不改变数据库或事实协议。

## 已实际尝试的候选

同输入使用上轮两个真实 Android ASR 来源：长会议 12 题，短会议／笔记 8 题。不同候选会重复同一题；回放次数不等于独立题目数量。原始文件仅在本机 `output/q2-two-stage-20261022/`，不是生产 prompt 或业务源码。

本轮共 9 批、96 次真实问题回放，只有 20 个独立问题；未把重复回放计为新增测试覆盖，也未宣称人工 95% 通过。

1. **先选原文、再回答，两次模型调用。** 无新增模型或上下文；保留 UTF-8 身份、哈希、原文和最多八条引用约束。13 项独立候选合同测试通过，但真实回放错用中间价格、把数量单位混成金额，短会议概述也会拒答。更短等待不等于质量提高，未采用。
2. **直接用 native chat 结构化接口。** 简单系统指令对照可通过，但复杂问答仍出现不符合 Schema 的数组／对象结构，未采用。
3. **显式 Qwen3.5 角色格式 + raw completion grammar。** 简单交互／后台指令和结构对照可通过，但完整回放仍有漏答、笔记归责和无关引用，未采用，Provider 格式分派及专属测试全部撤回。
4. **单一答案数组协议。** 删除重复的顶层 answer 和固定 c1–c4 槽位，在内部数组中表达必要分句，不改公开 Q2 envelope 或历史。分别用显式角色和当前原生 Provider 回放。答案通常更简洁，预付比例可回答，但仍有旧比例混入、尾款／综合条件漏答，以及把笔记事项当作发言人工作的退步，未采用。

以上失败是语义或合同实测失败，不是部署阻塞；不能将它们合并成“均已完成”。没有把失败候选做成备用开关，没有改生产 provider、模型、GPU、日程、整理、ASR 或手机数据。因此没有为纯诊断工具另发一个 APK。

## 必须保留的归因纠正

曾看到 `/api/show` 的模板为 `{{ .Prompt }}`，且一次系统／用户冲突测试采用用户值，因而过早推断“系统提示没有送入模型”。这个推断已撤回，不能被下轮当作根因：

- 实机 Ollama `0.24.0` 的 [GenerateHandler 源码](https://raw.githubusercontent.com/ollama/ollama/v0.24.0/server/routes.go) 在无自定义模板、非 raw 的普通消息路径调用 `chatPrompt`／内置渲染器，不只看展示出来的模板字符串。
- 同一生产 `/api/generate`，仅将系统文本从 5 字扩展到 27,005 字，真实 `prompt_eval_count` 从 29 增至 15,029。流式和非流式均如此，证明系统文本实际进入了输入。
- 生产版重复随机指令对照出现交互失败、后台通过；候选对照也不能代替完整业务回放。模型“收到但未遵守”与“没有收到”必须区分，不能凭一次回答反推传输丢字段。
- [Ollama 结构化输出文档](https://docs.ollama.com/capabilities/structured-outputs) 说明格式约束的使用方式；[JSONSchemaBench](https://arxiv.org/abs/2501.10868) 也分别考察效率、约束覆盖与内容质量。这里只借鉴评估维度，不把论文或 JSON 合法率当本应用的质量通过证据。

## 当前保留的工程结果

- `tools/quality/probe_generation_contract.py` 使用无隐私随机标识、交互／后台两种调用，分别检查 JSON shape 和系统指令遵循。预期答案不藏在 Schema 的 enum／const 中，不能靠解码语法强迫探针通过。
- 输出字段为 `system_instruction_followed`，不是 `seen`。探针失败不能证明提示词传输丢失，也不等于服务宕机，不能据此自动重启。
- 五种探针 oracle 回归区分遵循、用户值覆盖、额外字段、类型错误和非法 JSON；和既有 Provider／Q2／引用回归共 98 项通过。数字不是语义合格样本数。
- `probe_question_reader.py` 可在私有候选目录加载依赖，并记录实际 operation；不再为导入候选而把临时代码拷进生产。

# Q2 无损来源传输与真实端到端提速

## 本轮交付

采用 gzip-base64 压缩 Q2 小型完整来源请求，来源内容、身份、哈希、权限、Task 和本机激活 fence 不变。服务端已部署；最终 Android **1.2.63 / 271** 已公开发布并由应用内检查更新识别。未安装真机，未提交或推送 Git。

这是传输性能切片，不是检索、生成或语义复核升级。长会议漏答、错误拒答、无关引用及笔记归责没有据此宣称通过。

## 先定位，未采用数据库猜测

此前模拟器同一真实问题从发送到保存为 20,115 ms，POST 19,133 ms，而生成与复核约9.3秒。此次以实际设备鉴权、现有225条转写、原问题，在只读备份的控制库副本上启动完整隔离 HTTP 路由；模型和 Provider 真实，禁止后台 worker、生产写库和无关路由。

- 3次隔离服务端请求耗时10,597 / 10,789 / 11,114 ms；客户端经 SSH loopback 为10,748 / 10,988 / 11,218 ms。
- 每次15次来源 schema ensure 合计仅128 / 136 / 138 ms，来源准备973 / 1,271 / 1,314 ms，reader 9,294 / 9,104 / 9,407 ms；来源加载25–28 ms，提交结果97–121 ms。
- 同样124,500字节的请求经公网 HTTPS 从电脑发送，也需要19,563 / 20,787 ms，说明延迟差不只发生在模拟器/JS。
- 未采用 schema-once 优化，没有把约9.8秒差额归因 SQLite。现有阶段计时不能进一步区分公网入口、上行链路和缓冲各自的占比。

## 变更合同

客户端新增 `questionSourcePayload.ts`，只在服务端宣告 `question_inline_gzip_v1` 时编码。压缩编码一次，仍由原传输 owner 发送一次 inline POST；没有失败后重传明文的旁路。

- 压缩前来源 JSON 最大256 KiB、最多1,024段，约束与原 inline 合同一致。超过预算仍走现有 source-stream，不借压缩扩大 inline 接纳范围。
- 小于1 KiB或压缩后无收益保留原表示；这是发送前的大小选择，不是请求失败 fallback。
- gzip使用固定mtime、level 1；依赖固定为 fflate 0.8.3 / base64-js 1.5.1。浏览器/Hermes 路径实际运行；不新增 native 依赖或常驻模型。[实现来源](https://github.com/101arrowz/fflate)
- 服务端 `question_source_codec.py` 严格验证编码、声明长度和有界 base64；解压最多声明长度+1，验证EOF、CRC、尾随数据、连接帧、UTF-8、JSON数组及段数。大小不符、压缩炸弹或损坏帧失败关闭。
- 解码后每段仍通过原 `Q2ReaderSource`、逐字哈希、来源指纹、鉴权和绑定校验；拒绝明文/压缩混用及与已提交 stream 混用。压缩字段不成为第二份持久来源。
- AES-GCM 临时来源、租约、清理义务、Task幂等及手机SQLite结果 owner 原样保留。日志不新增来源正文、请求头或引用；诊断结果只写权限0600的私有证据。
- 原269客户端仍实际使用明文协议，因此保留该已知活跃兼容表示。没有备用模型、备用来源或新UI设置。

## 真实性能证据

同一来源与同一问题的重复测量，不是十个独立质量样本，也不是p95或全会议负载基准：

| 边界 | 原请求 | 无损压缩请求 |
| --- | --- | --- |
| 电脑→隔离完整HTTP | 10,748 / 10,988 / 11,218 ms | 11,290 / 11,342 ms |
| 电脑→公开HTTPS→真实模型 | 19,563 / 20,787 ms | 14,232 / 14,178 / 12,446 ms |
| 5562应用owner→公开HTTPS→SQLite | 原记录20,115 ms | 14,553 / 15,081 ms |

电脑诊断使用Node zlib，完整请求从124,500降至34,854字节；Android使用fflate，123,805字节的来源数组压缩后base64数据为36,396字节，后者不含外层请求。编码器不同，不能混称同一个字节数。Hermes实测5次编码为59.683 / 57.751 / 41.796 / 42.798 / 48.313 ms。

应用两次真实PUT为598 / 779 ms、POST为13,652 / 13,955 ms；真实答案保存后，3条唯一引用仍属于当前来源，225段转写保留。强退并重开后完整会话与保存结果相同。共10次完整HTTP及2次应用问答、24次实际生成/复核调用；10次HTTP结果除新建操作ID（snapshot/task/stream）外完整相同。

这是当前问题约5秒的可复现改善，不宣称所有网络、超256KiB来源或所有长会议均已达到该速度。模型本身约9秒的生成/复核成本未改变。

另尝试旧短会议的含笔记问题，但本机内容已不可准备，应用在发送前返回本机不可用，HTTP调用为0。没有为通过测试重建或清理会议；本次不声称笔记归责的真实语义验收通过。通用编码合同覆盖转写/笔记/附件的逐字元数据往返，仅证明无损，不替代语义审阅。

# 智能会议与老记内部交流说明

更新时间：2026-07-07  
适用范围：智能会议记录项目、“老记”一句话待办项目，以及相关语音识别工具  
文档定位：供内部沟通、需求对齐、后续开发排期和项目交接使用。

## 1. 总体说明

当前需要对齐的是两个相关但定位不同的项目：

| 项目 | 目录 | 定位 |
| --- | --- | --- |
| 会议 | `smart-meeting-ai/` 会议相关前后端模块 | 面向会议场景，完成实时转写、混合 ASR、说话人管理、会议总结和导出 |
| 老记 | `smart-meeting-ai/` 老记相关前后端模块 | 面向办公和个人事务场景，用一句话或短语音创建日程、待办和提醒 |

`ASR/` 目录不是一个独立业务项目，而是语音识别工具模块。它可以为会议、老记或其他页面提供轻量语音输入能力，但内部交流和后续排期应围绕“会议”和“老记”两个项目展开。

内部交流时建议把它们分开理解：

- 会议：核心任务是优化混合转写模式，并提升会议总结速度和质量。
- 老记：核心任务是明确功能需求、提升智能化、从会议工程中独立出来，并推进 App 化。
- ASR 工具：作为语音输入和语音识别能力的支撑，不单独作为主项目管理。

## 2. 支撑工具：ASR 轻量语音识别模块

### 2.1 需求背景

ASR 工具模块的核心需求是让用户可以通过浏览器麦克风直接输入语音，并将语音实时转换为文本。它适合用在搜索框、聊天框、短指令、表单备注、智能助手唤醒等轻量场景。

该模块不依赖后端 ASR 服务，不需要额外部署模型，主要利用浏览器已有能力完成语音识别。

### 2.2 已实现能力

当前 `ASR/` 目录包含：

- `asr_helper.js`：语音识别封装类
- `demo.html`：浏览器演示页面
- `README.md`：迁移与集成说明

核心能力包括：

- 调用浏览器原生 `SpeechRecognition`
- 支持中文识别，默认语言为 `zh-CN`
- 支持临时识别结果和最终识别结果
- 提供开始、结束、错误、结果回调
- 前端页面可以根据回调更新按钮状态和识别文案

### 2.3 技术实现

ASR 模块基于浏览器原生 Web Speech API，主要使用：

- `SpeechRecognition`
- `webkitSpeechRecognition`
- `interimResults`
- `onresult`
- `onstart`
- `onend`
- `onerror`

它的优点是集成简单、成本低、部署轻；限制是能力受浏览器和系统环境影响较大。

推荐浏览器：

- Chrome
- Edge
- Safari 部分支持

Firefox 默认不支持该能力。

### 2.4 使用方式

典型接入流程：

1. 将 `ASR/asr_helper.js` 复制到目标项目。
2. 页面中准备状态显示区域和语音按钮。
3. 初始化 `ASRHelper`，配置 `onStart`、`onResult`、`onEnd`、`onError` 回调。
4. 用户点击按钮后调用 `asr.start()`。
5. 在 `onResult` 中处理临时文本和最终文本。

典型使用场景：

- 短语音输入
- 语音搜索
- 语音填写备注
- 对话式页面输入
- 快速验证语音交互原型

### 2.5 当前限制

- 需要 HTTPS 或可信 localhost 环境才能稳定获取麦克风权限。
- 识别质量依赖浏览器实现和系统环境。
- Firefox 默认不支持。
- 更适合短语音，不适合长会议实时转写。
- 如果需要企业级准确率、热词、说话人识别、长音频处理，应使用后端 ASR 或本地模型链路。

## 3. 两个业务项目：会议与老记

### 3.1 项目定位

Smart Meeting AI 当前包含两条业务主线，也就是后续内部推进时应重点关注的两个项目：

- 会议项目：把会议音频转成可检索、可总结、可导出的会议资产。
- 老记项目：把一句自然语言或短语音转换为结构化日程、待办和提醒。

它面向企业会议、办公协作和个人事务管理场景，目标不是单纯“录音转文字”，而是把语音内容进一步变成结构化信息，包括发言记录、会议结论、行动项、日程和提醒。

### 3.2 当前入口

| 模块 | 地址 | 说明 |
| --- | --- | --- |
| 会议记录 | `https://localhost:5179` | 主会议系统前端 |

| 会议后端 | `http://127.0.0.1:8020` | 主 FastAPI 服务 |

通过 VS Code Remote SSH 使用时，需要在端口面板转发 `5179`、`5181`、`8020`、`8035`，浏览器访问本地 `localhost`，请求会转发到远程服务器。

## 4. 智能会议记录功能

### 4.1 需求目标

智能会议记录的目标是把一次会议从“临时音频”转换为“可沉淀的会议资产”。它覆盖会议创建、实时转写、说话人识别、阶段总结、最终总结、行动项提取和文档导出。

典型用户需求包括：

- 会议过程中实时看到字幕。
- 会后快速得到会议纪要。
- 区分不同发言人。
- 提取关键结论和行动项。
- 支持导出和归档。
- 后续可对接企业知识库、项目管理系统或日历系统。

### 4.2 已实现能力

当前会议侧已经具备演示级闭环：

- 会议创建与会议列表
- 实时会议页面
- 历史会议详情
- 离线音频转写页面
- Qwen ASR、Whisper/FunASR 等实验页面
- 说话人管理入口
- 会议总结与导出入口
- REST 接口和 WebSocket 实时推送接口

主要页面包括：

- `/`：会议列表与入口页
- `/meeting/:id/active`：默认实时会议页
- `/meeting/:id/qwen`：Qwen ASR 实时模式页
- `/meeting/:id/whisper`：Whisper/FunASR 相关实验页
- `/meeting/:id/offline`：离线音频转写页
- `/meeting/:id/summary`：会议总结与导出页
- `/speakers`：声纹和说话人管理页

### 4.3 实时转写路线

系统已经验证三类实时转写路线：

| 模式 | 作用 | 当前判断 |
| --- | --- | --- |
| FunASR 实时模式 | 负责低延迟字幕和会议过程记录 | 适合作为实时主链路 |
| Qwen ASR 模式 | 负责更强语义理解和句段修正 | 单独实时使用成本偏高 |
| FunASR + Qwen 混合模式 | FunASR 先出实时文本，Qwen 做句段增强 | 推荐作为企业化方向 |

建议后续采用混合路线：FunASR 保证会议现场实时反馈，Qwen 在句段级做上下文修正、术语补全、标点整理、摘要和行动项提取。

### 4.4 说话人识别

系统包含说话人和声纹管理入口，可以维护说话人身份，并在会议转写中尝试绑定发言人。

当前状态仍偏实验，需要继续增强：

- 多人会议准确率
- 背景噪声下的识别稳定性
- 多人重叠说话处理
- 短句和插话场景
- 前端人工修正和声纹库反哺

### 4.5 会议总结

会议总结支持最终总结展示和文档下载，可复用本地 Qwen 模型或外部 LLM 服务。

当前需要重点优化的是长会议总结体验。由于本地大模型推理受显存、上下文长度和队列影响，会议总结可能较慢。建议改造成异步任务：

- 提交总结任务后立即返回任务 ID
- 前端展示任务进度
- 阶段拆分为转写清洗、段落聚合、摘要生成、行动项提取、文档生成
- 支持取消、重试和切换模型

### 4.6 文档导出

现有会议详情页提供转写文档和总结文档下载入口。后续建议增强：

- DOCX、PDF、Markdown 多格式导出
- 保留说话人、时间戳、行动项、决议和风险点
- 支持企业会议模板，例如周会、需求会、评审会、复盘会

## 5. 老记一句话待办功能

### 5.1 需求目标

老记是一个语音优先的智能日程入口。用户不需要填写复杂表单，只要说出或输入一句话，系统就把自然语言压缩成可确认、可编辑、可保存的结构化日程。

示例：

```text
老记老记，下周三下午两点和周总开会，要讨论硬件相关问题
```

系统应自动解析：

- 事件标题
- 日期
- 开始时间
- 结束时间
- 重复类型
- 补充描述
- 是否需要追问
- 是否存在冲突

### 5.2 已实现能力

当前老记已支持：

- 一句话自然语言创建日程
- 规则解析 + 本地大模型混合解析
- 模糊时间追问
- 文本补充和语音补充
- 本地 FunASR 一次性短音频转写
- 麦克风和系统音频测试入口
- 音频波形与录音状态反馈
- 确认表单
- 保存到 SQLite 日程库
- 月历视图和日程列表
- 重复事件动态展开
- 冲突轻提示
- 保存成功反馈与撤销

### 5.3 技术路线

老记采用“规则优先，本地大模型兜底”的混合策略。

规则解析适合高确定性表达，例如：

- 明天下午三点提醒我发项目周报
- 每周一上午十点团队例会
- 7月25日下午两点开会
- 月底前找财务确认报销的事

本地大模型适合口语化、模糊或更复杂的表达，例如：

- 下周找个时间和周总聊一下硬件预算
- 本月内抽空整理一下项目材料
- 月初把上个月报销和硬件预算一起过一下

当前本地模型默认使用 `qwen3:8b` 做结构化解析、语义理解和追问判断。32B 总结模型不作为老记默认链路，避免显存占用过高和响应延迟过长。

### 5.4 短语音 ASR 链路

老记前端已经从浏览器 Web Speech 改为更可控的本地一次性转写链路：

1. 浏览器采集麦克风或系统音频。
2. 前端整理为 16kHz 单声道 WAV。
3. 调用后端 `/api/laoji/asr/transcribe`。
4. 后端复用本地 FunASR 完成中文转写。
5. 转写结果写入主输入框或追问补充框。

当前还做了老记唤醒词同音归一化：

```text
老纪 / 老计 / 老季 / 牢记 / 小记 -> 老记
```

这可以降低 ASR 把“老记老记”识别成“老纪老纪”时对解析链路的影响。

### 5.5 当前接口

老记接口统一使用 `/api/laoji/*` 前缀。旧版 `/api/schedule/*` 暂时保留为兼容入口。

主要接口：

| 接口 | 说明 |
| --- | --- |
| `POST /api/laoji/parse` | 解析一句自然语言为日程草稿 |
| `POST /api/laoji/clarify` | 对当前草稿进行追问补充 |
| `POST /api/laoji/asr/transcribe` | 一次性短音频转写 |
| `POST /api/laoji/events` | 保存确认后的日程 |
| `GET /api/laoji/events?year=2026&month=7` | 查询指定月份日程并展开重复事件 |

## 6. 系统技术架构

### 6.1 前端

前端采用 React + TypeScript + Vite，当前会议记录和老记共用同一个前端工程。通过不同路由和代理端口分别访问：

- 会议记录：`https://localhost:5179`
- 老记：`https://localhost:5181/laoji`

前端代理由 `frontend/serve_with_proxy.py` 提供，负责 HTTPS 静态文件服务以及 API/WebSocket 代理。

### 6.2 后端

后端采用 FastAPI，包含两个主要入口：

- `app.main:app`：会议主服务
- `app.laoji.main:app`：老记轻量服务

会议主服务包含会议、音频、转写、总结、说话人和 WebSocket 等接口。老记轻量服务只挂载老记 API，避免启动时加载会议实时转录、声纹或 WhisperLiveKit 等较重能力。

### 6.3 模型与算法能力

当前系统涉及的模型和算法能力包括：

- FunASR：会议实时转写和老记短语音转写
- Qwen ASR：短音频或辅助识别服务
- Qwen LLM：句段修正、日程解析、会议总结和行动项提取
- 说话人识别/声纹：用于会议发言人绑定
- 音频清洗与 VAD：用于提升 ASR 输入质量

### 6.4 数据与任务

当前本地运行保留了 SQLite 数据库和必要模型文件。架构文档中也保留了更完整的生产方向：

- PostgreSQL：会议、转写、总结等结构化数据
- Redis：缓存、任务状态、WebSocket 推送辅助
- Celery：异步转写、总结和文档生成任务
- 本地文件系统：音频、导出文档和模型文件

后续企业化时，应把长耗时能力从同步接口迁移到任务队列。

### 8.3 当前主要限制

会议侧：

- 实时 ASR 需要固定主链路，建议收敛到 FunASR + Qwen 混合模式。
- 说话人识别仍需要更多真实多人会议验证。
- 总结链路在长会议和本地大模型占用时可能较慢。
- 部分历史实验链路仍在代码中，后续需要进一步收敛。
- 权限、日志、监控、任务队列和企业部署规范仍待完善。

老记侧：

- 仍与会议系统共享前端工程，后续可以独立成 PWA 或 Web App。
- 模糊时间追问目前偏规则化，还不是完整槽位状态机。
- 冲突检测是轻提示，没有主动改期建议。
- 未接入真实提醒推送和外部日历同步。
- 多用户隔离、账号权限和个人记忆库尚未完成。

ASR 轻量模块：

- 受浏览器兼容性和权限影响。
- 不适合长会议转写。
- 缺少热词、声纹、长音频和企业级控制能力。

## 9. 后续需要完成的内容

### 9.1 会议项目专项

会议项目下一阶段最重要的是三件事：优化混合模式、会议总结提速、建立指标评测。建议按 P0/P1/P2 推进。

| 优先级 | 任务 | 目标 | 说明 |
| --- | --- | --- | --- |
| P0 | 优化混合模式 | 固化会议实时转写主链路 | FunASR 负责低延迟实时字幕，Qwen 负责句段修正、术语补全、标点整理和语义增强 |
| P0 | 会议总结提速 | 让会议总结从“能用”变成“可等待、可交付” | 先做异步任务和分段总结，再评估模型量化、模型分层和微调 |
| P0 | 指标评测 | 建立判断优化是否有效的标准 | 覆盖延迟、准确率、术语召回、说话人识别、总结事实一致性和用户可读性 |
| P1 | 说话人识别增强 | 提升多人会议可用性 | 补齐真实多人会议、噪声、插话、重叠说话场景评测 |
| P1 | WebSocket 稳定性 | 提升长会议稳定性 | 增加自动重连、音频缓冲、断点续传和错误恢复 |
| P1 | 导出模板完善 | 提升会后交付质量 | 支持会议纪要、行动项、决议、风险点和企业模板 |
| P2 | 企业知识库/项目系统对接 | 形成会议后业务闭环 | 将会议结论和行动项同步到知识库、项目管理或日历系统 |

P0-1 优化混合模式：

- 固化 FunASR + Qwen 混合模式作为推荐主链路。
- FunASR 负责实时字幕和低延迟反馈，避免现场等待。
- Qwen 负责句段修正、术语补全、标点整理和语义增强。
- 保留 FunASR 原始文本和 Qwen 修正文本，便于对比和回退。
- 明确什么时候触发 Qwen 增强，例如按句段、按静音间隔、按时间窗口或会议阶段触发。
- 优化 WebSocket 推送策略，区分实时临时结果、稳定结果和增强结果。

P0-2 会议总结提速：

- 将会议总结改为异步任务，避免前端长时间等待。
- 对总结流程拆阶段：转写清洗、分段聚合、章节摘要、行动项提取、最终文档生成。
- 优先评估模型量化方案，降低显存占用和推理延迟。
- 评估小模型日常总结 + 大模型高质量总结的分层方案。
- 根据会议总结样例积累数据，后续评估微调或 LoRA 微调的必要性。
- 对不同会议长度设置不同策略，短会议直接总结，长会议先分段再合并。
- 增加总结进度、耗时统计、失败重试和任务取消。

P0-3 指标评测：

- 建立标准测试集，覆盖单人、多人、噪声、口音、专业术语和长会议。
- ASR 指标：首字延迟、稳态延迟、字错误率、关键词召回率、专业术语准确率。
- 混合模式指标：Qwen 修正耗时、修正后可读性、信息删减率、原文保真度。
- 说话人指标：说话人识别准确率、短句识别率、重叠说话处理效果。
- 总结指标：生成耗时、事实一致性、行动项召回率、幻觉率、人工可用率。
- 工程指标：接口耗时、WebSocket 断连率、任务失败率、GPU 占用和队列长度。

P1/P2 补齐项：

- 对 WebSocket 增加自动重连、音频缓冲和断点续传。
- 补齐说话人识别的真实多人会议评测。
- 完善会议导出模板，支持会议纪要、行动项、决议和风险点。

### 9.2 老记项目专项

老记下一阶段同样建议按 P0/P1/P2 推进。优先顺序是：先明确需求和最小闭环，再做智能化与独立化，最后推进 App 和外部生态。

| 优先级 | 任务 | 目标 | 说明 |
| --- | --- | --- | --- |
| P0 | 明确功能需求 | 防止功能发散，先定义老记到底解决什么问题 | 明确它是日程助手、待办助手、提醒助手，还是会议行动项承接工具 |
| P0 | 最小可用闭环 | 形成可演示、可验证、可迭代的核心流程 | 输入一句话、解析草稿、追问补全、确认保存、查看日程 |
| P0 | 指标评测 | 判断老记是否真的变聪明 | 覆盖解析准确率、追问命中率、ASR 准确率、保存成功率和端到端耗时 |
| P1 | 智能化增强 | 从规则解析升级为更自然的对话式安排 | 槽位追问、冲突建议、时间理解、个人记忆和智能摘要 |
| P1 | 独立出来 | 从会议工程中拆出老记 | 独立后端、独立前端入口、独立数据、独立部署和日志 |
| P1 | App / PWA 开发 | 验证移动端真实使用体验 | 优先 PWA 或 Web App，后续评估原生 App |
| P2 | 外部日历和企业工具同步 | 形成真实办公闭环 | ICS、CalDAV、飞书、企业微信、Outlook、Google Calendar |
| P2 | 多用户和个人记忆 | 支持长期个人使用 | 账号、联系人、项目名、地点、常用偏好和多端同步 |

P0-1 明确功能需求：

- 明确老记的核心定位：一句话日程助手、待办助手、提醒助手，还是会议行动项承接工具。
- 梳理高频使用场景，例如日程创建、截止提醒、周期任务、会议后行动项、语音备忘。
- 明确最小可用闭环：输入一句话、解析草稿、追问补全、确认保存、提醒或同步。
- 明确哪些能力第一阶段必须做，哪些留到第二阶段，例如外部日历同步、个人记忆、多端同步。
- 明确移动端使用方式，是 PWA、原生 App，还是先做 Web App 包装。

P0-2 老记指标评测：

- 语音指标：短语音 ASR 字错误率、热词识别率、端到端转写耗时。
- 解析指标：标题、日期、时间、重复规则、描述字段的抽取准确率。
- 追问指标：缺失槽位识别率、追问问题有效率、补充后更新成功率。
- 日程指标：保存成功率、冲突检测准确率、重复日程展开准确率。
- 体验指标：从输入到可确认草稿的耗时、用户修改次数、撤销率。

P1-1 智能化：

- 把追问升级为槽位状态机，逐步补齐标题、日期、时间、持续时间、重复规则、地点、参与人和提醒。
- 区分事件时间、截止时间和提醒时间。
- 从冲突提示升级为主动改期建议。
- 建立联系人、项目名和地点的个人记忆库。
- 增强自然语言理解，支持更口语、更模糊、更复杂的表达。
- 给老记短语音 ASR 增加热词和端点检测，例如老记、财务、报销、周总、硬件、周报。
- 增加确认前的智能摘要，让用户知道系统理解了什么。

P1-2 独立出来：

- 让 `app.laoji.main` 真正独立部署，只加载短音频 ASR、日程解析、日程存储和 Ollama 8B 调用。
- 从会议主服务中拆出老记后端依赖，减少启动时间和运行耦合。
- 将 `/api/laoji/*` 固化为独立 API 契约。
- 将 `/laoji` 前端页面整理成独立前端入口或独立工程。
- 单独管理老记的数据表、配置、日志、健康检查和部署脚本。

P1-3 App 开发：

- 优先将 `/laoji` 整理为 PWA 或独立 Web App，验证移动端交互。
- 适配手机端录音、权限、触控、日历视图和保存反馈。
- 后续评估原生 App 或跨端框架开发。
- 增加 ICS 导出、CalDAV、飞书、企业微信、Outlook 或 Google Calendar 同步。
- 为 App 准备稳定接口，包括登录、日程查询、日程保存、撤销、提醒和同步。

### 9.3 产品层面

- 明确会议记录和老记的目标用户、使用场景和边界。
- 梳理会议前、会议中、会议后的完整工作流。
- 明确老记是独立日程助手，还是会议行动项的延伸能力，或两者兼具。
- 补齐用户账号、团队空间、会议权限和数据隔离。
- 明确导出、分享、归档、审计等企业需求。

### 9.4 工程层面

- 统一错误码、日志格式和健康检查。
- 把端口、模型路径、数据目录、CORS、HTTPS 证书等配置化。
- 收敛历史实验链路，保留清晰的推荐链路。
- 为核心接口增加自动化测试和回归样例。
- 将长耗时任务纳入队列，避免同步接口阻塞。

### 9.5 企业化部署

- 使用 PostgreSQL 替代本地 SQLite 作为正式数据存储。
- 引入 Redis 和 Celery 处理异步任务。
- 将模型服务部署到独立 GPU 节点。
- 使用 Nginx 或 Ingress 统一入口。
- 增加监控指标，包括 GPU 占用、队列长度、接口耗时、WebSocket 连接数和错误率。
- 补齐认证、授权、数据脱敏、审计日志和导出权限控制。
